오늘 날짜를 기준으로 `_posts/` 폴더에 새 블로그 포스트 파일을 생성해줘.

사용자가 주제만 말하더라도 추가 질문 없이 제목, 카테고리, 태그, 내용을 모두 채워서 바로 파일을 만들어줘.
사용자가 명시적으로 제공한 정보는 그대로 쓰고, 나머지는 주제에서 추론해서 채울 것.

## 파일명 규칙

`YYYY-MM-DD-{title을-영어-소문자-kebab-case로}.md`

## frontmatter 형식

```yaml
---
title: {제목}
date: YYYY-MM-DD HH:MM:SS +0900
categories: [{상위 카테고리}, {하위 카테고리}]
tags: [{태그1}, {태그2}]
---
```

## 카테고리 규칙

- categories는 최대 2개 (Chirpy 제한)
- 기존 카테고리를 우선 사용해서 일관성을 유지할 것

**현재 사용 중인 카테고리:**

| 상위 | 하위 | 용도 |
|------|------|------|
| AI | Claude | Claude Code, AI 개발 도구 관련 |
| 개발 | AI | AI 활용 개발 일반 |
| 개발 | 성능 | 프론트엔드 성능 최적화 |
| 개발 | 테스트 | 테스트 코드, QA |
| 개발 | Flutter | Flutter/Dart 개발 |
| Career | Interview | 취업, 면접 준비 |
| CodingTest | Hash | 코딩테스트 해시 문제 |
| Study | Algorithm | 알고리즘 학습 정리 |

## 태그 규칙

- 기술 키워드는 영어 소문자: `performance`, `flutter`, `claude`, `ai`
- 코딩테스트/알고리즘 관련은 한국어 허용: `코딩테스트`, `해시`, `배열`
- 기존 포스트에서 쓰인 태그를 재사용해서 일관성을 유지할 것

## 제목 패턴

제목도 본문처럼 담백하게, 글에서 다루는 내용을 그대로 쓴다.

- 무엇을 했는지, 무엇에 대한 글인지를 짧은 명사구나 "~하기"로 쓴다: `Claude Code로 만든 채용공고 트래커`, `Flutter 개발 환경 세팅하기`
- "제목 — 부제" 형식은 시리즈에만 쓴다. 시리즈가 아닌 글에는 부제를 붙이지 않는다
- 질문형·훅 제목을 쓰지 않는다: "어디서부터 시작할까", "무엇이 다른가", "어떻게 써야 잘 쓰는 걸까"
- 수식어나 과장을 넣지 않는다: "완벽 정리", "총정리", "제대로", "꿀팁", "~의 모든 것"
- 카테고리 prefix 방식: `[알고리즘] 제목`, `[해시] 제목` — 코딩테스트/학습 포스트에 사용
- 시리즈 방식: `시리즈명 (1) — 부제`. 부제에는 이번 편 내용을 질문이 아닌 짧은 명사구로 쓴다
  - 예: `프론트엔드 성능 최적화 (2) — 번들 크기 줄이기`

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| CLAUDE.md vs AGENTS.md — 무엇이 다른가 | CLAUDE.md와 AGENTS.md 차이 |
| Claude Code — 어떻게 써야 잘 쓰는 걸까 | Claude Code 사용법 정리 |
| 프론트엔드 성능 최적화, 어디서부터 시작할까 (1) — 측정과 진단 | 프론트엔드 성능 최적화 (1) — 측정과 진단 |

## 내용 작성 틀

아래 구조를 기준으로 작성할 것. 참고 문체: https://devpro.kr/posts/google-search-console-analytics/

```
{서론 (선택): 왜 이 주제를 다루게 됐는지 1~2문장}
헤딩 없이 본문 맨 앞에 둔다. 동기는 사용자가 말한 이유만 쓰고, 모르면 지어내지 말고 물어본다.
인사("안녕하세요"), 질문형 서론("~한 적 있으신가요?"), 글 소개("이 글에서는 ~를 정리합니다")는 쓰지 않는다.

## 1. {첫 번째 내용}

## 2. {본문 섹션}

## 3. {본문 섹션}

...
```

마무리 섹션은 따로 두지 않는다. 마지막 섹션의 내용이 끝나면 글도 끝난다. 필요하면 마지막에 주의사항이나 (이미 있는) 다음 편 안내를 한두 문장으로 둔다.

**글의 성격:** 주제에 대한 정보 전달용 글이다. 대화 기록이나 작업 기록을 요약하는 글이 아니다.

- 세션 대화, 작업 내용, 사용자가 준 자료는 소재로만 쓴다. 대화 순서나 질문 목록을 그대로 섹션으로 옮기지 않는다
- 먼저 주제를 처음 접하는 독자가 알아야 할 내용과 순서를 정하고, 그 구조에 맞춰 쓴다. 대화에 없던 내용이라도 주제에 필요하면 넣는다 (예: FastAPI 입문 글이면 FastAPI가 무엇인지, `/redoc`, 파이썬 버전별 문법 차이)
- 대화 중에 나온 곁가지(curl 옵션, 에디터 설정, IDE 선택, 내 맥의 파이썬 버전 등)는 주제에 필요할 때만 넣는다
- 대화에서 만든 코드는 예시 코드로 쓴다. 설명에 맞게 다듬어도 된다
- 대화에 없던 내용을 넣을 때는 사실인지 확인하고 쓴다

**어투:** 담백한 합니다체 설명글. 내 경험담보다 다루는 대상(도구, 문법, 절차)을 차분하게 설명한다. 꾸미지도, 일부러 친근하게 굴지도 않는다.

- 어미는 "~합니다", "~입니다"로 쓴다. 해요체나 반말을 섞지 않는다
- 주어는 다루는 대상이다. "저는 ~했습니다"는 꼭 필요할 때만 쓴다
- 절차는 한 문장에 한 동작씩, 현재형으로 쓴다: "좌측 메뉴의 설정 탭을 클릭합니다.", "`uv add fastapi`로 설치합니다."
- 결과를 확인하는 방법을 쓴다: "~가 나타나면 연결이 완료된 것입니다."
- 문단은 2~4문장으로 짧게 쓴다. 한 문단에 한 가지 내용만 둔다
- 날짜, 숫자, 버전, 걸리는 시간처럼 실제 값이 있으면 그 값을 쓴다
- 감정, 감상, 경험담을 넣지 않는다. 사용자가 말하지 않은 경험은 지어내지 않는다
- 극적인 전개나 꾸민 표현을 쓰지 않는다. ("그날 밤의 악몽", "~와 마주하게 됩니다")
- 문장 끝에 덧붙이는 말을 넣지 않는다. ("~하는 셈입니다", "~인 편입니다")
- 교훈형 마무리나 캐치프레이즈를 쓰지 않는다. ("결국 핵심은 ~입니다", 교훈 목록)
- "가장 중요한 건", "핵심은", "확실히", "획기적인", "놀랍게도" 같은 수식어·과장은 뺀다
- 독자에게 하는 안내는 참고·주의 블록에서만 짧게 한다: "~를 참고하면 좋습니다", "하루 정도 여유를 두고 확인해 보시기 바랍니다"

예시:

```
# 이렇게 쓰지 않는다 (경험담·꾸민 표현)
맥에 깔려 있던 파이썬이 3.9라서 좀 당황했습니다. 다행히 uv라는 멋진 도구를 알게 되었습니다.

# 이렇게 쓴다
macOS에 기본으로 설치된 파이썬은 3.9입니다. 프로젝트마다 다른 버전을 쓰려면 uv로 버전을 지정합니다.
`uv init`에 `--python 3.13` 옵션을 주면 해당 프로젝트에서만 3.13을 사용합니다.
```

**형식:**
- 헤딩은 번호를 붙인다: `## 1. 연결하면 무엇이 좋을까?`, `## 2. uv로 프로젝트 만들기`. 하위는 `###`
- 헤딩에 이모지를 붙이지 않는다. "~의 부재", "~의 구조적 한계" 같은 명사형 보고서 헤딩은 쓰지 않는다
- 문단으로 풀어 쓰는 걸 기본으로 한다. 표와 목록은 비교·나열이 필요할 때만 쓴다
- 볼드는 한 글에 몇 군데만 쓴다
- 섹션 사이에 `---` 구분선을 넣지 않는다. 번호 헤딩으로 구분한다
- 코드 블록에는 언어 명시: ` ```javascript `, ` ```bash ` 등
- 참고 링크, 주의사항은 인용 블록(`>`)으로 짧게 쓴다. Chirpy 강조 블록은 한 글에 1~2개 정도:
  - `{: .prompt-info }` — 참고/부연 설명
  - `{: .prompt-tip }` — 팁/권장 방법
  - `{: .prompt-warning }` — 주의사항
  - `{: .prompt-danger }` — 위험/오류 유발 패턴

## 분량 및 시리즈 판단

- 포스트 한 편의 적정 분량은 **1,000~2,000자** (읽는 데 5~10분)
- 주제가 방대해서 한 편에 담기 어려우면 자동으로 시리즈로 분리할 것
  - 시리즈로 판단하는 기준: 주요 섹션이 4개를 넘거나, 각 섹션이 독립적으로 완결될 수 있을 때
  - 분리 시 제목은 시리즈 방식(`시리즈명 (1) — 부제`)으로 짓고, 각 편을 순서대로 모두 생성
  - 2편 이후 첫 줄에 이전 편 링크 추가
  - 다음 편 예고는 다음 편을 같이 쓰거나 이미 있을 때만 넣는다. 아직 쓰지 않은 편은 예고하지 않는다

## 기타 규칙

- 사용자가 내용을 직접 제공하면 그대로 사용하고, 없으면 주제에 맞게 초안을 작성해줄 것
- 같은 날짜에 같은 주제의 파일이 이미 있는지 확인 후 생성

## 완료 후 요약

파일 생성이 완료되면 아래 항목을 사용자에게 요약해줄 것:

- **파일명**: 생성된 파일 경로
- **제목**: 포스트 제목
- **카테고리 / 태그**
- **섹션 구성**: 작성된 본문의 주요 섹션 목록
