채용 플랫폼마다 올라오는 공고가 달라서, 지원할 곳을 한눈에 보려면 어딘가에 모아야 한다. 그래서 이직 준비를 시작하면서 Notion에 표를 하나 만들었다. 공고를 볼 때마다 행을 추가하고 회사명과 포지션, 마감일을 적고, 필수기술과 우대기술을 멀티셀렉트에서 골랐다. 주요업무는 공고를 읽고 요약해 적었다.

한 건에 몇 분씩 든다. 바쁠 때는 링크만 붙여넣고 넘어갔더니 그런 행이 서른 건 넘게 쌓였다. 링크만 있는 행은 열어보기 전까지 아무 정보가 없어서, 어디부터 볼지 정하려면 하나씩 다시 열어야 하고 그 사이 마감이 지난 것도 섞여 있다.

그래서 이 정리를 Claude Code에 넘겼다. 공고를 만나면 링크를 주고 커맨드를 부르는 것까지가 내 몫이고, 읽고 뽑고 채우는 건 그쪽이 한다. 파이썬 스크립트를 쓰거나 API 토큰을 발급하지 않았고, 커넥터를 한 번 연결한 뒤로는 마크다운만 적었다.

## 🧩 커맨드와 스펙 문서로 만들었다

Claude Code에는 `.claude/commands/`에 마크다운을 두면 슬래시 커맨드가 되는 기능이 있다. 그 파일에 절차를 적어두면 `/명령이름`으로 부를 수 있다.

이 도구는 커맨드 네 개로 되어 있다.

| 커맨드 | 하는 일 |
|---|---|
| `/analyze-job` | 공고 1건을 분석해 Notion 카드 생성 |
| `/process-inbox` | URL만 담아둔 행을 모아 한꺼번에 정리 |
| `/score-jobs` | 프로필 대비 적합도를 전 행에 다시 채움 |
| `/check-jobs` | 링크를 다시 읽어 마감·변경을 점검 |

내가 쓴 건 이 커맨드 파일들과 규칙 문서뿐이다. Notion에 쓰는 것은 MCP가, 공고를 읽는 것은 `WebFetch`가 한다. 이미 쓰고 있는 Claude Code 세션에 붙어 돌기 때문에 API 토큰을 따로 발급하거나 서버를 띄울 일이 없다.

![아키텍처](/assets/img/job-notion-architecture.svg)

칸반과 필터, 모바일 UI는 Notion이 이미 갖고 있어서 화면도 만들지 않았다. 자동화만 붙였다.

---

## 📐 규칙은 스펙 문서 한 곳에 둔다

커맨드가 네 개인데 셋이 같은 추출 규칙을 쓴다. 각 커맨드에 규칙을 적어두면 하나를 고칠 때 나머지가 어긋난다.

그래서 규칙을 스펙 문서로 빼고 커맨드가 그걸 참조하게 했다.

```
prompts/analysis-spec.md   추출·매핑 규칙    ← /analyze-job, /process-inbox
prompts/fit-spec.md        적합도 산정 규칙   ← /analyze-job, /score-jobs
```

커맨드 파일에는 절차만 남고, 무엇을 어떻게 뽑을지는 스펙에 있다.

> 프롬프트를 여러 파일에 복사해두면 그게 곧 부채가 된다. 커맨드가 늘어날수록 어느 쪽이 최신인지 알 수 없게 된다.
{: .prompt-tip }

## 🧮 점수를 Claude에게 묻지 않았다

공고가 쌓이면 결국 "어디부터 볼지"가 문제다. 그래서 내 프로필 대비 요건 적합도를 0~100으로 매겨 컬럼에 채우기로 했다.

처음에는 Claude에게 점수를 물어볼 생각이었다. 그런데 다시 돌리면 순위가 흔들린다. 같은 공고에 어제는 82점, 오늘은 76점이 나오면 정렬 기준으로 쓸 수 없다.

그래서 스펙 문서에 가중치 계산을 못박았다.

| 항목 | 배점 | 계산 |
|---|---|---|
| 필수기술 매칭 | 60 | `60 × 보유 / 전체` |
| 경력 부합 | 20 | 요구 연차와의 차이로 단계 부여 |
| 우대기술 커버 | 20 | `20 × 보유 / 전체` |
| 대체 불가 스택 미보유 | −20 | 항목당 −10 |

Claude가 하는 일은 공고에서 필수기술과 경력을 뽑아내는 것까지다. 그 값을 숫자로 바꾸는 계산은 정해진 규칙이 한다. 점수만 남기면 되짚을 수 없어서 근거도 한 줄 같이 적는다.

```
필수 5/6 (미보유: SSR) · 경력 3년+ 충족 · 우대 2/4
```

> 합격 확률이 아니다. 실제 합격은 지원자 풀·TO·타이밍처럼 공고에 없는 변수로 갈린다. 이 점수는 쌓인 공고를 어디부터 볼지 정하는 참고값이다.
{: .prompt-info }

> 적합도는 프로필 품질을 그대로 물려받는다. 보유기술을 넉넉하게 적으면 대부분의 공고가 요건을 만족해 점수가 80점대에 뭉치고 정렬이 무의미해진다. 실제로 쓴 기술만 적어야 변별력이 생긴다.
{: .prompt-warning }

## 🔍 공고는 살아 있는 데이터다

한 번 정리하고 끝이 아니다. 마감일이 바뀌고, 공고가 내려가고, 자격요건이 조용히 수정된다. 그래서 링크를 다시 읽는 커맨드를 붙였다.

여기서 원칙을 하나 정했다. 확실한 것만 고치고, 애매한 것은 알려준다.

| 대상 | 동작 |
|---|---|
| 마감된 공고 | 상태를 `마감`으로 바꾸고 적합도를 비운다 |
| 마감일 변경·재게시 | 직접 반영 |
| 공고 내용 변경 | 감지해서 보고만. 속성은 안 건드린다 |

내용 변경을 자동 반영하지 않는 이유는 재분석이 위험하기 때문이다. 추출 편차로 기존 값을 조용히 덮어쓸 수 있고, 필수기술이 바뀌면 적합도까지 연쇄로 틀어진다. "바뀐 것 같다"까지만 알리고 재분석은 내가 판단한다.

> 쓰고 나서 바로 조회하면 옛 값이 온다. 인덱스가 늦게 따라오기 때문이다. 방금 채운 값을 확인할 때는 조회 대신 페이지를 직접 읽어야 한다.
{: .prompt-warning }

---

## ✋ 없는 것을 마감으로 단정하면 안 된다

판정 규칙에서 제일 조심한 부분이다. 페이지가 404거나 응답이 애매할 때 마감으로 처리하면 살아있는 공고를 죽인다.

실제로 겪었다. 어떤 회사 공고가 하루는 404였는데 다음 날 정상으로 돌아왔다. 그날 자동 처리했다면 그 공고는 마감으로 묻혔다.

지금은 게시 상태가 명확히 종료일 때만 마감으로 확정하고, 404나 봇 차단은 "확인 필요"로만 보고한다.

> 지원을 이미 넣은 공고는 마감 처리를 하지 않는다. 지원한 회사가 채용을 마쳐 공고를 내리는 건 정상인데, 그때 상태를 바꾸면 지원 기록과 경과일 추적이 끊긴다.
{: .prompt-warning }

---

## 📏 포맷 차이는 변경이 아니다

내용 변경을 감지하려면 저장된 본문과 새로 읽은 원문을 비교해야 한다. 처음 돌렸을 때 34건 중 14건이 "변경됨"으로 나왔다. 그런데 13건이 실제 변경이 아니었다.

등록할 때 다듬은 값과 원문을 그대로 비교한 탓이다. 채용 사이트 원제목에는 연차나 한영 중복 표기가 붙어 있는데(`Frontend Engineer 3년 이상`) 등록 시 정규화해 저장했고, 초기 일괄 등록분은 본문까지 요약돼 있었다. 원문 우대사항 9개가 한 줄로 묶인 행을 문장 단위로 비교하면 전부 "삭제됨"으로 나온다.

그래서 커맨드에 판별 절차를 먼저 뒀다. 비교 가능한 행인지 확인한 뒤 비교하고, 줄바꿈·글머리표·마크다운 이스케이프 같은 포맷 차이는 변경으로 세지 않는다. 건너뛴 행은 몇 건인지 반드시 보고에 밝힌다 — 조용히 생략하면 전부 점검한 것처럼 보인다.

## ✅ 정리

1. `.claude/commands/`에 마크다운만 두면 도구가 된다. 쓰기는 MCP, 읽기는 `WebFetch`가 맡으니 스크립트도 토큰 발급도 서버도 없다.
2. 커맨드 여러 개가 같은 규칙을 쓰면 스펙 문서로 빼고 참조하게 한다. 복사해두면 그게 부채가 된다.
3. 재돌릴 때 값이 흔들리면 정렬 기준으로 쓸 수 없다. 숫자는 규칙으로 고정하고 추출만 모델에 맡긴다.
4. 점수만 남기면 되짚을 수 없다. 근거를 한 줄 같이 적는다.
5. 확실한 것만 고치고 애매한 것은 보고한다. 자동 반영이 조용히 기존 값을 덮는 쪽이 더 나쁘다.
6. 응답이 없다는 것과 끝났다는 것은 다르다. 404를 마감으로 단정하면 살아있는 것을 죽인다.
7. 포맷 차이를 변경으로 세면 전부 변경으로 나온다. 비교 전에 비교 가능한지부터 판별한다.
