Claude Code를 처음 쓰면 "그냥 물어보면 되는 거 아닌가"라고 생각하기 쉽다. 그런데 똑같은 작업을 요청해도 프롬프트 방식에 따라 결과가 완전히 달라진다. 몇 달 써오면서 효과적이었던 방식을 정리했다.

---

## 맥락을 충분히 줘라

Claude Code는 레포를 직접 탐색하기 때문에 코드 구조는 스스로 파악한다. 하지만 **왜** 고쳐야 하는지, **어떤 정책**이 적용돼야 하는지는 알 수 없다. 그건 반드시 직접 설명해줘야 한다.

```
# 나쁜 예
> discount 함수 고쳐줘.
```

이렇게 요청하면 Claude가 코드를 읽고 "문제가 없어 보이는데요"라고 하거나, 엉뚱한 부분을 수정할 수 있다.

```
# 좋은 예
> discount 함수에서 할인율 적용 순서가 잘못됐어.
  현재는 세금 계산 후 할인이 적용되는데,
  정책상 세금 전에 할인이 먼저 적용돼야 해.
  예를 들어 10만원 상품에 10% 할인이면
  9만원에 부가세 10%를 붙여서 99,000원이 나와야 해.
  관련 테스트도 함께 수정해줘.
```

비즈니스 규칙, 제약 조건, 기대하는 결과값까지 구체적으로 줄수록 한 번에 올바른 결과가 나온다. "왜"가 빠진 요청은 절반짜리 요청이다.

---

## 작업 범위를 먼저 파악하게 해라

큰 작업을 바로 수행하게 하면 예상치 못한 파일이 수정되거나, 되돌리기 어려운 상태가 될 수 있다. 수정 전에 반드시 범위 파악 단계를 거친다.

```
> API 응답 타입을 snake_case에서 camelCase로 바꾸려고 해.
  수정이 필요한 파일 목록을 먼저 파악해줘.
  실제 수정은 아직 하지 마.
```

Claude가 영향받는 파일 목록을 정리해주면 훑어본다. 예상보다 범위가 넓거나, `legacy/` 같이 건드리면 안 되는 디렉토리가 포함돼 있으면 그때 제외 조건을 추가해서 다시 요청한다.

실제로 이 방식으로 진행했을 때, 처음엔 몰랐던 서드파티 연동 파일이 범위에 포함돼 있는 걸 미리 잡아낸 적이 있다. 그냥 수정했으면 런타임 에러로 발견했을 문제였다.

---

## CLAUDE.md를 잘 써라

`CLAUDE.md`는 Claude Code가 대화 시작 시 읽는 파일이다. 처음엔 "그냥 매번 설명하면 되지 않나"라고 생각했는데, 세팅해두고 나서 경험이 완전히 달라졌다.

잘 쓴 `CLAUDE.md`는 이런 내용을 담는다.

```markdown
# 프로젝트명

## 개요
Next.js 14 + TypeScript. App Router 사용. pnpm 패키지 매니저.
외부 API: 결제는 Toss Payments, 인증은 자체 JWT.

## 디렉토리 구조
- `src/app/` — App Router 페이지 및 API 라우트
- `src/components/` — 공통 UI 컴포넌트 (shadcn/ui 기반)
- `src/lib/` — 유틸리티, API 클라이언트, 훅
- `src/types/` — 전역 타입 정의

## 코딩 규칙
- 커밋 메시지: Conventional Commits, 영어
- 컴포넌트: 함수형, named export만 사용
- 스타일: Tailwind CSS, cn() 유틸리티 사용
- 테스트: Vitest + Testing Library, 같은 디렉토리에 `*.test.ts`

## 절대 건드리지 말 것
- `src/legacy/` — 구버전 코드, 마이그레이션 완료 전까지 수정 금지
- `src/lib/payments/toss.ts` — 결제 연동 핵심 파일, 수정 시 반드시 사람에게 먼저 확인
```

반대로 이런 내용은 넣지 않는 게 낫다.

- 코드에서 바로 읽을 수 있는 것 (함수 시그니처, 타입 정의 등)
- 자주 바뀌는 정보 (현재 진행 중인 작업, 담당자)

> `CLAUDE.md`는 살아있는 문서다. 구조나 컨벤션이 바뀌었는데 파일이 낡아있으면 오히려 없는 것보다 혼란을 준다. PR에 코드 변경과 함께 `CLAUDE.md` 업데이트를 습관으로 만드는 게 좋다.
{: .prompt-warning }

## 결과물은 반드시 리뷰해라

Claude Code가 빠르게 만들어줘도, 로직이 의도와 다를 수 있다. 특히 아래 경우는 꼭 직접 확인한다.

- **비즈니스 규칙이 얽힌 로직** — 정책이 코드에 녹아있는 부분
- **외부 시스템과 연동되는 코드** — API 호출, DB 쿼리, 메시지 큐 발행
- **보안 관련 부분** — 인증 토큰 처리, 입력 검증, 권한 체크

빠르게 결과를 얻는 게 목적이지만, **리뷰 없이 그냥 올리는 건 안 된다.** Claude Code를 쓴다고 코드 리뷰가 줄어드는 게 아니라, 리뷰할 코드가 빠르게 생기는 것이다.

> 테스트 코드도 마찬가지다. 케이스는 잘 만들어주지만, 기대값이 정책에 맞는지는 직접 검토해야 한다.

## 큰 작업은 단계로 나눠라

한 번에 너무 많은 걸 요청하면 중간에 실수가 쌓이고, 어디서 잘못됐는지 파악하기 어려워진다. 큰 작업은 체크포인트를 두고 단계적으로 진행한다.

세션 기반 인증을 JWT로 교체하는 작업을 예로 들면, 이렇게 나눴다.

```
> 1단계: 현재 인증 모듈 구조를 파악해줘.
  세션이 어떻게 생성되고 검증되는지 흐름을 정리해줘.

> 2단계: JWT 토큰 생성/검증 유틸리티를 src/lib/auth/jwt.ts에 만들어줘.
  access token은 15분, refresh token은 7일 만료.
  기존 세션 코드는 아직 건드리지 마.

> 3단계: 로그인 엔드포인트부터 JWT 방식으로 교체해줘.
  기존 세션 코드는 주석으로 남겨줘. 나중에 롤백할 수 있게.

> 4단계: 나머지 인증 미들웨어를 교체해줘.
  3단계 결과를 확인한 다음에 진행할게.

> 5단계: 기존 세션 관련 테스트를 JWT 방식으로 업데이트해줘.
```

각 단계마다 결과를 확인하고 넘어가니, 3단계에서 미처 생각 못 했던 소셜 로그인 연동 부분을 발견해서 계획을 수정할 수 있었다. 한 번에 다 요청했으면 얽혀서 풀기 어려웠을 상황이었다.

## Skills로 반복 작업을 자동화해라

같은 프롬프트를 반복하고 있다면 Skills로 만들어두는 게 낫다. `.claude/skills/{name}/SKILL.md`에 자연어로 동작을 정의하면 `/name`으로 호출할 수 있다.

팀에서 만들어두면 유용한 Skills 예시:

```
.claude/
└── skills/
    ├── pr/         # git diff를 읽고 PR 설명 자동 작성
    ├── changelog/  # 커밋 히스토리로 릴리즈 노트 생성
    ├── review/     # 변경 파일에 대한 리뷰 포인트 정리
    └── test/       # 특정 파일의 테스트 케이스 초안 작성
```

나 혼자 쓸 때도 유용하지만, 팀에 공유하면 진짜 가치가 생긴다. 레포에 커밋해두면 팀원 모두가 동일한 방식으로 쓸 수 있다. PR 설명의 품질이 일관되게 올라가는 게 체감된다.

---

## 도구의 역할을 구분해라

Claude Code를 쓴다고 모든 걸 맡길 수 있는 건 아니다. 기대치를 정확히 설정해야 실망도 없고 실수도 줄어든다.

| 잘 되는 것 | 사람이 해야 하는 것 |
|---|---|
| 버그 원인 파악 및 수정 | 아키텍처 결정 |
| 여러 파일에 걸친 리팩토링 | 비즈니스 정책 판단 |
| 테스트 케이스 초안 작성 | 테스트 기대값 검토 |
| 낯선 코드베이스 구조 파악 | 코드 리뷰 및 최종 승인 |
| 커밋 메시지 / PR 설명 작성 | 기술 부채 우선순위 결정 |

Claude Code는 개발자를 대체하는 게 아니다. 반복적이고 맥락 의존적인 작업을 빠르게 처리해주는 도구다. 잘 쓰면 중요한 판단에 쓸 시간이 늘어난다.
