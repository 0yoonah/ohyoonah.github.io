## 하네스 엔지니어링이란

하네스(harness)는 원래 말에 씌우는 마구(馬具)를 뜻한다. 말의 힘을 제어하고 원하는 방향으로 이끌기 위한 장치다. Claude Code에서도 마찬가지다. AI의 능력을 그대로 쓰는 게 아니라, 프로젝트에 맞게 제어하고 구조화해서 원하는 방향으로 동작하게 만드는 것이다.

> **에이전트 = 모델 + 하네스**
>
> 모델은 Claude 자체의 능력이고, 하네스는 그 능력이 발휘되는 환경과 규칙이다. 모델이 아무리 뛰어나도 하네스 없이는 매번 다르게 동작하고, 실수를 반복하고, 컨텍스트를 잃는다.
{: .prompt-info }

### 프롬프트 엔지니어링과의 차이

흔히 AI를 잘 쓰려면 프롬프트를 잘 써야 한다고 한다. 틀린 말은 아니지만, 프롬프트는 대화 하나에만 유효하다. 대화가 끝나면 사라진다.

| | 프롬프트 엔지니어링 | 하네스 엔지니어링 |
|--|--|--|
| 유효 범위 | 대화 하나 | 프로젝트 전체 |
| 저장 방식 | 없음 (일회성) | 파일로 저장, 버전 관리 |
| 공유 | 불가 | 팀 전체 공유 가능 |
| 개선 방식 | 매번 다시 작성 | 실패 시 규칙에 반영 |

하네스는 누적된다. 에이전트가 실수했을 때 그 교훈을 `CLAUDE.md`나 `settings.json`에 반영하면, 다음번에는 같은 실수를 반복하지 않는다.

### 구성 요소

| 구성 요소 | 역할 |
|-----------|------|
| `CLAUDE.md` | 프로젝트 지침 — Claude가 대화 시작 시 자동으로 읽는 문서 |
| `settings.json` | 권한, 훅, 환경 변수 설정 |
| Skills | 커스텀 슬래시 명령어 (`/plan`, `/deploy` 등) |
| Memory | 대화 간 지속되는 컨텍스트 저장소 |
| Hooks | 이벤트 발생 시 자동 실행되는 셸 명령어 |

이 구성 요소들을 조합하면 에이전트에게 역할을 부여하고, 파이프라인처럼 동작하는 멀티 에이전트 시스템을 만들 수 있다.

## 에이전트 파이프라인

각 에이전트는 독립적인 역할을 갖고, 다음 에이전트에게 컨텍스트를 넘기며 파이프라인처럼 동작한다.

![하네스 에이전트 파이프라인](/assets/img/harness-pipeline.svg)

## 프로젝트 디렉토리 구조

```
.claude/
├── settings.json
├── skills/
│   ├── plan.md       # /plan      — 기획 에이전트
│   ├── dev.md        # /dev       — 개발 에이전트
│   ├── qa-white.md   # /qa-white  — 화이트박스 QA
│   ├── qa-black.md   # /qa-black  — 블랙박스 QA
│   └── deploy.md     # /deploy    — 배포 에이전트
└── memory/
    ├── MEMORY.md
    └── current-spec.md   # 에이전트 간 공유 스펙
CLAUDE.md
```

> 에이전트들은 `current-spec.md`를 공유 저장소로 사용한다. `/plan`이 스펙을 작성하면, 이후 에이전트들이 순서대로 읽으며 작업을 이어받는다.
{: .prompt-tip }

## 기획 에이전트 (`/plan`)

사용자의 요청을 받아 구현 가능한 스펙 문서로 변환한다.

```markdown
# plan

사용자의 요청을 분석해서 개발 스펙을 작성해줘.

1. `.claude/memory/current-spec.md`가 이미 존재하면 내용을 먼저 확인하고,
   덮어써도 되는지 사용자에게 물어봐
2. 요청 사항을 구체적인 기능 단위로 분해
3. 각 기능의 입력/출력/엣지케이스 정의
4. 작업 순서와 의존 관계 정리
5. 결과를 `.claude/memory/current-spec.md`에 저장

## 출력 형식
- 기능 목록 (체크리스트)
- API 또는 컴포넌트 인터페이스 정의
- 예상 작업량 (S/M/L)
- 주의사항

스펙 작성이 끝나면 "/dev로 개발을 시작할 수 있습니다."라고 알려줘.
```

사용 예시:

```
/plan 유저가 게시글에 좋아요를 누를 수 있는 기능을 추가해줘
```

기획 에이전트는 좋아요 API 엔드포인트, DB 스키마 변경, UI 컴포넌트 인터페이스를 정의하고 `current-spec.md`에 저장한다.

---

## 개발 에이전트 (`/dev`)

기획 에이전트가 남긴 스펙을 읽고 코드를 구현한다.

```markdown
# dev

`.claude/memory/current-spec.md`를 읽고 스펙에 따라 코드를 구현해줘.

1. 스펙 파일을 먼저 읽어서 구현할 내용 파악
2. 기존 코드 스타일과 패턴에 맞춰 구현
3. 각 기능 구현 완료 후 스펙의 해당 항목을 `[ ]` → `[x]`로 업데이트
4. 구현 완료 후 변경된 파일 목록을 요약

## 주의사항
- 스펙에 없는 기능은 임의로 추가하지 않는다
- 타입은 반드시 명시한다
- 기존 테스트가 깨지지 않도록 한다
```

---

## 화이트박스 QA 에이전트 (`/qa-white`)

코드 내부를 직접 보고 정적으로 검증한다. 타입, 린트, 유닛 테스트가 주 역할이다.

```markdown
# qa-white

코드를 내부적으로 검토하고 정적 분석을 실행해줘.

1. `git diff main`으로 변경사항 파악
2. 스펙(`.claude/memory/current-spec.md`)과 구현 내용 대조
3. 아래 항목 순서대로 확인:
   - 타입 체크: `npm run typecheck`
   - 린트: `npm run lint`
   - 유닛 테스트: `npm run test`
4. 실패 항목은 직접 수정 후 재실행
5. 수정해도 해결되지 않으면 `/dev`에게 재작업 요청
6. 모두 통과하면 "/qa-black으로 블랙박스 검증을 시작할 수 있습니다."라고 알려줘

## 리포트 형식
- 통과 항목 ✓
- 수정한 항목 (수정 내용 요약)
- 주의가 필요한 사항
```

---

## 블랙박스 QA 에이전트 (`/qa-black`)

코드 내부는 보지 않고 실제 사용자 관점에서 기능을 검증한다. 스펙에 정의된 시나리오대로 동작하는지, 엣지케이스에서 어떻게 반응하는지를 확인한다.

```markdown
# qa-black

코드를 보지 말고, 실제 사용자 입장에서 기능을 검증해줘.

1. 스펙(`.claude/memory/current-spec.md`)에서 기능 목록 파악
2. 각 기능을 사용자 시나리오 기준으로 확인:
   - 정상 흐름: 스펙대로 동작하는가
   - 엣지케이스: 빈 값, 중복, 권한 없음 등
   - UX: 에러 메시지가 사용자에게 명확한가
3. 문제 발견 시 `/dev`에게 재작업 요청
4. 모두 통과하면 "/deploy로 배포할 수 있습니다."라고 알려줘

## 리포트 형식
- 검증한 시나리오 목록
- 통과 ✓ / 실패 ✗ 여부
- 실패 항목의 재현 조건
```

---

## 배포 에이전트 (`/deploy`)

QA를 통과한 코드를 빌드하고 배포한다.

```markdown
# deploy

코드를 빌드하고 프로덕션에 배포해줘.

1. `.claude/memory/current-spec.md`의 작업 목록에 미완료(`[ ]`) 항목이 없는지 확인
   미완료 항목이 있으면 배포를 중단하고 사용자에게 알려줘
2. 현재 브랜치와 변경사항 확인
3. 빌드: `npm run build`
4. 빌드 성공 시 배포: `npm run deploy`
5. 헬스체크 엔드포인트 응답 확인
6. 결과 요약 (배포 시각, 버전, 주요 변경사항)

## 실패 처리
- 빌드 실패 시 에러 로그를 출력하고 중단
- 헬스체크 실패 시 롤백 명령어 안내
```

## 가드레일 설정

에이전트가 자율적으로 동작할수록 예상치 못한 행동을 할 가능성도 커진다. `settings.json`의 권한 설정으로 명시적인 경계를 만들어두는 것이 중요하다.

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git add *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push --force *)",
      "Bash(rm -rf *)",
      "Bash(DROP TABLE *)"
    ]
  }
}
```

허용 목록에 없는 명령어는 실행 전에 승인을 요청하고, 차단 목록에 있는 명령어는 아예 실행되지 않는다.

> 에이전트에게 자율성을 줄수록 가드레일은 더 촘촘해야 한다. 돌이키기 어려운 작업(force push, 파일 삭제, DB 조작)은 반드시 deny 목록에 넣어두자.
{: .prompt-warning }

## Hooks로 단계 전환 자동화

`settings.json`의 훅을 활용하면 Claude가 응답을 마칠 때마다 자동으로 명령어를 실행할 수 있다.

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "cat .claude/memory/current-spec.md | grep -c '\\[ \\]' | xargs -I{} echo '미완료 항목: {}개'"
          }
        ]
      }
    ]
  }
}
```

Claude가 응답을 마칠 때마다 미완료 항목 수를 출력해서 진행 상황을 추적한다.

## 실제 워크플로

```bash
# 1. 기획
/plan 검색 자동완성 기능을 추가해줘

# 2. 개발
/dev

# 3. 화이트박스 QA
/qa-white

# 4. 블랙박스 QA
/qa-black

# 5. 배포
/deploy
```

> 각 단계가 명확히 분리되어 있어서 특정 단계만 재실행하거나, 스펙을 수정하고 개발부터 다시 시작하는 것도 가능하다.
{: .prompt-tip }

## 실패를 하네스에 반영하기

처음부터 완벽한 하네스는 없다. 에이전트를 실제로 운용하면서 실패 패턴을 발견하고, 그걸 규칙으로 쌓아가는 과정이 하네스 엔지니어링의 본질이다.

| 실패 패턴 | 반영 위치 |
|-----------|-----------|
| 자꾸 실수하는 행동 | `CLAUDE.md` 주의사항에 추가 |
| 실행하면 안 되는 명령어 | `settings.json` deny 목록에 추가 |
| 특정 단계에서 놓치는 항목 | 해당 스킬 파일 체크리스트에 추가 |

> 에이전트가 실수했을 때 "왜 이랬지?" 하고 넘기지 말고, 같은 실수가 반복되지 않도록 하네스에 기록하는 습관이 중요하다.
{: .prompt-tip }

---

## 정리

하네스는 에이전트가 동작하는 환경과 규칙이다. 그 위에 역할이 명확한 에이전트들을 설계하면, 하나의 Claude가 모든 것을 판단하게 두는 것보다 훨씬 예측 가능하고 안정적인 파이프라인이 만들어진다.

Skills로 역할을 정의하고, Memory로 컨텍스트를 연결하고, Hooks로 자동화하고, 실패에서 규칙을 쌓아가면 — 개발 프로세스 전체를 Claude Code 위에서 운용할 수 있다.
