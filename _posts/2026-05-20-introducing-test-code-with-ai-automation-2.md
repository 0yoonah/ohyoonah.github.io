[1편](/posts/introducing-test-code-with-ai-automation)에서는 왜 테스트가 필요한지, AI를 쓰더라도 테스트가 중요한 이유를 정리했다. 이번 글에서는 실제로 AI를 활용해 테스트를 작성하는 방법과 CI/CD 자동화 설정을 다룬다.

---

## AI로 테스트 초안 만들기

테스트 도입의 가장 큰 장벽은 **시간**이다. 코드는 있는데 테스트를 새로 짜려면 의도를 파악하고, 케이스를 정리하고, 코드를 작성하는 시간이 든다.

AI가 가장 효과적인 지점이 여기다.

#### 유틸 함수 테스트 자동 생성

```
> calculateDiscount 함수를 읽고 테스트 케이스를 작성해줘.
  경계값, 예외 케이스, 정상 케이스를 모두 포함해줘.
```

Claude Code는 함수 구현을 읽고 어떤 입력이 들어올 수 있는지 분석해서 케이스를 뽑아낸다. 놓치기 쉬운 경계값(0, 음수, 최대값 등)도 함께 제안해준다.

```typescript
// AI가 생성한 테스트 초안
describe('calculateDiscount', () => {
  it('정상 할인율 적용', () => {
    expect(calculateDiscount(10000, 10)).toBe(9000);
  });

  it('할인율 0%는 원가 반환', () => {
    expect(calculateDiscount(10000, 0)).toBe(10000);
  });

  it('할인율 100%는 0 반환', () => {
    expect(calculateDiscount(10000, 100)).toBe(0);
  });

  it('음수 가격은 에러', () => {
    expect(() => calculateDiscount(-1000, 10)).toThrow();
  });

  it('할인율 범위 초과는 에러', () => {
    expect(() => calculateDiscount(10000, 101)).toThrow();
  });
});
```

> AI는 구현을 읽고 테스트를 짜기 때문에, 구현이 틀렸으면 테스트도 틀린 값을 기대한다. 기대값이 실제 비즈니스 정책과 맞는지 반드시 사람이 확인해야 한다.
{: .prompt-warning }

#### 버그 수정 후 회귀 테스트

버그를 고친 뒤 바로 물어본다.

```
> 방금 수정한 내용을 보고,
  이 버그가 재발했을 때 잡을 수 있는 테스트를 작성해줘.
```

수정 내용을 컨텍스트로 읽어서, 어떤 조건에서 터졌는지 기반으로 테스트를 만들어준다. 버그 수정과 테스트 작성을 같은 흐름에서 처리할 수 있다.

---

## AI 활용 시 주의할 점

#### 커버리지 숫자를 맹신하지 않는다

AI를 쓰면 커버리지를 빠르게 올릴 수 있다. 100줄짜리 유틸을 10분 만에 90% 커버리지로 만들 수 있다. 하지만 커버리지가 높다고 테스트가 좋은 게 아니다. 실행은 되지만 검증이 없는 테스트, 있을 법하지 않은 케이스만 가득한 테스트는 숫자만 채운다.

> 커버리지는 테스트가 얼마나 많은지를 보여줄 뿐, 얼마나 믿을 수 있는지는 보여주지 않는다.
{: .prompt-danger }

#### 목(Mock)을 과도하게 쓰지 않는다

AI는 외부 의존성이 있으면 자연스럽게 목으로 처리한다. API 호출, DB 조회, 파일 시스템 접근 같은 것들이 전부 목으로 대체된다.

테스트가 빠르고 안정적으로 돌아가는 건 좋지만, 과하면 문제가 생긴다. 목은 실제 동작을 흉내 내는 가짜다. 실제 DB 스키마가 바뀌거나 API 응답 형식이 달라졌을 때, 목을 쓴 테스트는 그 변화를 감지하지 못하고 그냥 통과한다.

비즈니스 로직이 외부 의존성과 얽혀 있는 부분은 목보다 실제에 가까운 테스트가 필요하다. AI가 목을 과도하게 만들었다면, 핵심 흐름에 해당하는 테스트는 직접 다듬는 게 낫다.

## CI/CD로 테스트 자동화하기

테스트를 짜는 것만큼 중요한 게 **자동으로 실행되는 환경**을 만드는 것이다. 로컬에서만 돌리면 빠뜨리기 쉽고, 팀 전체가 같은 기준으로 검증받지 못한다.

#### PR마다 자동 실행

GitHub Actions를 쓰면 PR이 열릴 때마다 테스트를 자동으로 돌릴 수 있다.

```yaml
# .github/workflows/test.yml
name: Test

on:
  pull_request:
    branches: [main, develop]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test -- --coverage
```

> 이렇게 설정하면 테스트가 실패할 경우 머지가 막힌다. "내 로컬에서는 됐는데"가 통하지 않는 환경이 만들어진다.
{: .prompt-tip }

#### AI로 워크플로우 초안 생성

CI 설정도 AI에게 맡길 수 있다.

```
> 이 프로젝트의 package.json을 보고
  PR마다 테스트를 자동 실행하는 GitHub Actions 워크플로우를 작성해줘.
  Node 버전과 패키지 매니저는 현재 프로젝트에 맞게 설정해줘.
```

프로젝트 구조를 읽고 패키지 매니저(npm/yarn/pnpm)와 테스트 스크립트를 파악해서 맞는 설정을 만들어준다. 직접 문서를 찾아가며 작성하는 것보다 훨씬 빠르다.

#### pre-commit 훅으로 커밋 전 검증

CI까지 가기 전에 로컬에서 먼저 걸러내는 방법도 있다. `husky`와 `lint-staged`를 쓰면 커밋 전에 변경된 파일과 관련된 테스트만 실행할 수 있다.

```json
// package.json
{
  "lint-staged": {
    "src/**/*.{ts,tsx}": ["jest --findRelatedTests --passWithNoTests"]
  }
}
```

전체 테스트를 돌리면 느리지만, 변경된 파일과 연관된 테스트만 골라 실행하면 커밋 흐름이 크게 느려지지 않는다.

## 팀에 안착시키는 법

환경을 갖추더라도 테스트 코드는 도입보다 유지가 어렵다. 처음엔 쓰다가 점점 안 쓰게 되는 경우가 많다. 기술보다 문화의 문제다.

도입 후 지속하기 위해 적용해보려는 방식이다.

**버그 수정 = 테스트 추가**
버그를 수정하면 반드시 그 케이스에 대한 테스트를 함께 PR에 포함한다. 별도 작업이 아니라 버그 수정의 일부로 보는 것이다.

**새 기능 = 핵심 로직 테스트 포함**
기능 전체를 커버할 필요는 없다. UI 렌더링이나 API 연동보다, 계산이나 판단이 있는 비즈니스 로직만이라도 테스트하는 것부터 시작한다.

**리뷰에서 테스트 코드를 함께 본다**
테스트 코드를 보면 구현 의도를 파악하는 데 도움이 된다. 리뷰 문화로 자리잡으면 테스트 작성이 자연스럽게 기대치가 된다.

---

테스트 코드 도입은 한 번에 완성되는 게 아니라 조금씩 쌓이는 거라는 걸 공부하면서 느꼈다.

AI를 활용하면 초안을 빠르게 만들 수 있어서 도입 진입 장벽이 낮아질 것 같다. 하지만 검증은 여전히 사람의 몫이다. AI가 짠 테스트가 통과했다는 건 "실행됐다"는 것이지, "올바르다"는 게 아니다.

좋은 테스트는 빠른 테스트가 아니라, 실제로 믿을 수 있는 테스트다. 도입하는 과정에서 겪는 것들은 계속 기록해나갈 생각이다.
