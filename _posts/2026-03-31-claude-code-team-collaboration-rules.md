Claude Code를 혼자 쓸 때와 팀에서 쓸 때는 다르다.

혼자라면 자기 방식대로 쓰면 그만인데, 팀에 도입하는 순간 "누가, 어떻게, 무엇을 맡길 건가"를 합의해야 한다. 규칙 없이 도입하면 오히려 혼란이 생긴다.

---

## 왜 규칙이 필요한가

합의 없이 도입하면 어떤 문제가 생길 수 있는지, 몇 가지 시나리오를 들면 이렇다.

- **컨벤션 불일치**: 팀원마다 다른 방식으로 프롬프트를 쓴다. `CLAUDE.md`가 없으면 Claude는 각자에게 다르게 동작한다. 누군가는 `interface`, 누군가는 `type`을 쓰는 코드를 만든다.

- **책임 소재 모호**: 리뷰어가 로직을 이해하기 어려운 코드를 발견했을 때 "Claude가 짠 거라서"라는 답이 돌아온다. 의도적인 결정인지 AI가 제안한 것인지 알 수 없는 상태가 반복된다.

- **검증 없는 머지**: 테스트 코드를 Claude가 생성했는데, Claude는 구현을 읽고 테스트를 짜기 때문에 구현이 틀렸으면 테스트도 틀린 값을 기대한다. 확인 없이 "테스트가 통과했으니 됐겠지"로 넘어가면 문제는 나중에 터진다.

도구가 문제가 아니라 **합의된 사용 방식이 없는 것**이 문제다. 팀 전체가 따를 규칙을 구체적으로 합의해야 한다.

---

## 1. CLAUDE.md를 팀 표준으로

`CLAUDE.md`는 Claude Code가 대화 시작 시 읽는 파일이다. 개인이 각자 관리하는 게 아니라 레포에 커밋해서 팀 문서로 다루는 것이 포인트다.

핵심은 **Claude에게 주는 지시가 곧 팀의 코딩 컨벤션**이 된다는 것이다. 말로만 "우리 팀은 named export 써"라고 하는 게 아니라, 그 규칙이 `CLAUDE.md`에 명시되면 Claude도, 사람도 같은 기준으로 코드를 쓴다.

```markdown
# 프로젝트명

## 기술 스택
React 16 + TypeScript 4 + Webpack 5 SPA.
상태 관리: Zustand (신규) / DVA-Redux (레거시, 마이그레이션 대상).
서버 상태: TanStack React Query. 스타일: Tailwind CSS + shadcn/ui.
패키지 매니저: yarn (npm/npx 사용 금지).

## 코딩 컨벤션
- 신규 컴포넌트: 함수형, TypeScript(.tsx), default export
- 모든 텍스트: `<Typography>` 컴포넌트 사용 (raw 태그에 텍스트 직접 작성 금지)
- 색상: CSS 변수 토큰 사용 (`text-gray900`, `bg-primary500` 등), 하드코딩 금지
- API 호출: `customAxios` 인스턴스 사용 (인증 헤더 자동 처리)
- 커밋 메시지: `CBK1-XXXX 설명` 형식 (Jira 티켓 ID 포함)
- i18n: 모든 노출 텍스트는 `useTranslation()` 처리, ko/en 번역 파일 모두 업데이트

## 레거시 — 신규 사용 금지
- `src/models/` — DVA/Redux 모델 (Zustand로 교체 중)
- Ant Design (`antd`) — shadcn/ui로 교체 중
- SWR — TanStack React Query로 교체 중
- LESS 파일 — Tailwind CSS로 교체 중

## 절대 건드리지 말 것
- 레거시 파일 수정 시 해당 부분만 현대화. 전면 리팩토링은 별도 Jira 티켓으로 분리.
- `main`, `staging` 브랜치 직접 커밋 금지 — 반드시 PR로 관리.
- feature 브랜치에 develop/staging을 merge하지 말 것 (브랜치 오염 방지).
```

`CLAUDE.md`는 수시로 업데이트하는 것이 좋다. 낡은 정보가 쌓이면 오히려 없는 것보다 해롭다. 단, 누가 언제 어떻게 수정할지도 팀 안에서 합의가 필요하다.

우리 팀은 이 부분에서 문제를 겪었다. 팀원 한 명이 `CLAUDE.md`를 수정해 팀 공유 없이 main에 머지했고, 나머지 팀원들은 파일이 바뀐 사실조차 몰랐다. `CLAUDE.md`가 feature 브랜치에 섞여 있으면 변경이 묻히기 쉽다는 걸 깨달은 계기였다. 이후 `CLAUDE.md` 수정 전용 공용 브랜치를 별도로 운영하고 있다. feature 브랜치에서 직접 수정하지 않고, 공용 브랜치에서 작업한 뒤 PR을 통해 팀 리뷰를 거쳐 주기적으로 머지한다.

> `CLAUDE.md` 관리 방식은 팀마다 다르다. 코드 변경과 함께 담는 방식, 공용 브랜치를 별도로 두는 방식 등 어떤 형태든 팀이 합의한 프로세스가 있으면 된다.

## 2. 공유 Skills로 작업 방식 통일

팀 안에서 반복되는 작업은 Skills로 만들어 레포에 커밋한다. 개인이 프롬프트를 각자 쓰는 게 아니라, 팀이 합의한 방식으로 요청하는 것이다.

```
.claude/
└── skills/
    ├── jira-branch/   # Jira 티켓 번호로 브랜치 자동 생성
    └── jira-pr/       # PR 생성 + Jira 티켓에 작업 요약 댓글 등록
```

우리 팀은 두 가지 Skills를 운영한다.

`/jira-branch CBK1-XXXX`를 실행하면 Jira 티켓 정보를 읽어 브랜치명을 자동으로 만들고 main에서 분기한다. `/jira-pr`은 변경사항을 분석해 PR을 생성하고, Jira 티켓에 작업 요약 댓글까지 한 번에 남긴다. 브랜치 네이밍 규칙이나 PR 양식 같은 팀 컨벤션이 Skills 안에 녹아 있어서 별도로 신경 쓰지 않아도 된다.

지금은 두 개지만, 팀 안에서 반복되는 작업이 생길 때마다 Skills로 만들어 나가는 것이 목표다. 규칙이 늘어나면 CLAUDE.md가 두꺼워지듯, 반복 작업이 늘어나면 Skills도 함께 쌓인다.

---

## 3. "Claude가 짰다"는 면죄부가 아니다

Claude Code로 생성된 코드도 **커밋하는 사람이 책임진다.** 리뷰가 필요하다는 건 당연한 얘기지만, 팀에서 쓸 때는 어떤 부분을 특히 봐야 하는지 구체적으로 합의해두는 게 중요하다.

### 놓치기 쉬운 상황들

- **테스트가 통과했는데 로직이 틀린 경우**: Claude는 구현을 읽고 테스트를 짜기 때문에, 구현 자체가 잘못됐으면 테스트도 틀린 값을 기대한다. 테스트가 통과해도 비즈니스 정책에 맞는지는 별개 문제다.

- **레거시 패턴을 그대로 따라 쓰는 경우**: Claude는 기존 코드 패턴을 참고해서 제안한다. 레거시 코드가 많은 프로젝트에서는 DVA나 Ant Design처럼 팀에서 걷어내고 있는 패턴을 그대로 쓴 코드를 만들어낼 수 있다.

- **번역 파일을 빠뜨리는 경우**: i18n 처리를 요청했을 때 한국어 번역 파일만 추가하고 영어 파일은 빠뜨리는 경우가 생긴다. 빌드 오류가 나지 않기 때문에 확인하지 않으면 그냥 넘어간다.

### PR 올리기 전 체크리스트

- [ ] 생성된 코드를 직접 읽었는가
- [ ] 레거시 패턴이 새로 쓰이고 있지는 않은가
- [ ] 비즈니스 로직이 포함된 부분은 직접 실행해서 확인했는가
- [ ] 번역 파일(ko/en)이 모두 업데이트됐는가
- [ ] 테스트 기대값이 실제 정책에 맞는지 확인했는가

### 리뷰어 관점

"이 코드 왜 이렇게 됐어요?"라는 질문에 "Claude가 짠 거라서요"는 답이 아니다. 작성자가 설명할 수 있어야 머지할 수 있다는 원칙을 팀 안에서 명시적으로 합의해두는 것이 중요하다.

---

## 4. 권한 범위를 명시한다

Claude Code는 기본적으로 파일을 읽고, 쓰고, 명령어를 실행한다. 팀 환경에서는 어디까지 허용할지 settings.json으로 미리 정해두는 것이 좋다. 허용 범위를 합의해두면 팀원이 실수로 의도치 않은 명령어를 실행하는 상황을 줄일 수 있다.

기준을 잡을 때 참고할 수 있는 분류다.

- **허용**: 로컬 빌드/테스트 명령어, 파일 읽기/쓰기, git 로컬 작업
- **확인 필요**: 환경변수가 포함된 스크립트, DB 마이그레이션
- **금지**: 프로덕션 환경에 직접 접근하는 명령어

설정 파일에 민감한 권한 정보가 포함될 수 있으므로 레포에 커밋하지 않고 개인 로컬 환경에서 관리하는 것을 권장한다.

---

## 5. 온보딩에 활용한다

새 팀원이 합류했을 때 Claude Code를 활용하면 코드베이스 파악 시간을 줄일 수 있다.

```
> 이 레포의 전체 구조를 파악해줘.
  핵심 비즈니스 로직이 어디에 있는지,
  주요 데이터 흐름은 어떻게 되는지 정리해줘.
  내가 처음 읽어야 할 파일 순서도 추천해줘.
```

`git clone` 후 막막하게 코드를 읽는 것보다, 이렇게 시작하면 전체 구조를 빠르게 잡을 수 있다. CLAUDE.md에 프로젝트 컨텍스트가 잘 정리돼 있을수록 온보딩에서도 효과가 크다.

---

## 마치며

규칙이 많아지면 부담스럽게 느껴질 수 있다. 하지만 합의된 규칙이 있으면 리뷰할 때 기준이 생기고, 새 팀원이 합류해도 빠르게 맞춰진다.

도구를 잘 쓰는 것보다, **팀이 같은 방식으로 잘 쓰는 것**이 더 중요하다.
